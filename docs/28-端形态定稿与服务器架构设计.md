# 端形态定稿与服务器架构设计（容量 v2：用户 8000 万+ / 题目 9000 万+）

> 版本 v2.0 ｜ 本档为**容量与端形态的权威口径**（v1 的 3000 万/4000 万作废，docs/03/27 中旧数字以本档为准）。
> 三部分：① 管理端/用户端形态定稿；② 服务器与部署架构设计；③ GitHub 大用户量项目的设计模式借鉴落地表。

## 1. 端形态定稿（管理端和用户端是什么）

### 1.1 结论总表

| 端 | 用户 | 形态 | 技术 | 优先级 | 理由（对标学科网实测） |
|---|---|---|---|---|---|
| **教师端**（主战场） | 教师/机构 | **PC Web**（自适应，兼容平板 H5） | Vue 3 + TS + Element Plus + KaTeX | M1-M2 现有 | 组卷/备课/导出是大屏复杂操作，学科网/组卷网教师主流程全部在 PC（实站走查 docs/26）；APP 只是辅助浏览 |
| **学生端** | 学生/家长 | **微信小程序优先 + APP**（uni-app 一码多端，H5 兜底） | uni-app + Vue 3 | M3 起步 | 刷题/错题/报告是碎片化场景，微信生态获客成本最低；橙子学同形态 |
| **管理端**（超管/运营） | 超管/运营/编辑/审核 | **PC Web 内部系统** | Vue 3（vben-admin 模式） | M1 现有 | 内部工具，浏览器即可，不做客户端 |
| 学校版 | 校管理员 | PC Web（复用管理端框架，独立权限域） | 同上 | P2 | 网校通形态：学校购买、教师全员开通 |
| 开放平台 | 第三方/学校系统 | API（网关 /open/**） | — | P3 | 学科网 open.xkw.com 同形态 |

### 1.2 分端职责边界（避免功能长错地方）

- **教师端独占**：组卷全流程（章节/知识点/智能/细目表）、试题篮、试卷存档下载、班级作业布置、录题上传、资源站下载。
- **学生端独占**：刷题练习、错题本、学情报告、作业完成、订正打卡；**做题数据经 Feign 回流教师端班级视图**。
- **两端共享**（同账号体系，角色决定视图）：会员/点数/券/订单、消息通知、AI 讲题。
- **管理端独占**：题库审核流、广告位/公告/系统设置、券模板/CDK/任务配置、订单退款、版权工单、数据看板。
- API 原则：一套 `/api/v1/**`，按角色鉴权（X-User-Id/X-User-Role 网关注入），**不为小程序单独建后端**——uni-app 与 Web 共用同一批接口，差异只在展示层。

### 1.3 端形态对架构的约束（设计取舍依据）

1. 小程序**无法长连接常驻、包体 ≤2MB 主包**：题目渲染组件（KaTeX/图形）走分包+按需 CDN，AI 讲题用 SSE（小程序用 WebSocket 网关转接）。
2. PC Web 首屏要快：题目列表 SSR 不划算（登录态），用 **ES 直查 + Redis 热题缓存 + 骨架屏**，首屏 P90 < 1.5s。
3. 导出 PDF/Word 是重计算：**全部异步任务化**（download_task 表 + MQ + 渲染池），小程序端只轮询状态，不在端上拼文档。

## 2. 服务器设计（8000 万用户 / 9000 万题）

### 2.1 环境矩阵

| 环境 | 用途 | 规格 | 数据 |
|---|---|---|---|
| dev | 日常开发 | 本机 docker-compose（enterprise/ 现有） | 种子数据 |
| test | CI/联调 | 云上 4C16G×2 + 单实例中间件 | 每日重置 |
| staging | 预发/压测 | 与 prod 同拓扑 1/4 缩配 | 脱敏全量 |
| prod | 生产 | 见 2.3/2.4 | 全量 |

### 2.2 容量 v2 测算（决定拓扑的数字）

| 项 | 9000 万题 / 8000 万用户的推算 | 结论 |
|---|---|---|
| question 分片 | 9000 万 ÷ 64 逻辑槽 = **140 万行/槽**；8 物理库×8 表（64 槽，按学科垂直分库） | 单表 140 万行远离 2000 万警戒线，**8 库起步即可，扩到 16 库不改路由**（docs/27 §9.2 方案确认） |
| 用户域分片 | 8000 万 ÷ 256 槽（16 库×16 表）= **31 万行/表**，practice 90 天归档后常驻更低 | 16 库起步偏奢侈，**8 库×32 表=256 槽**同样成立；交易域独立库不分片 |
| 题目内容存储 | 9000 万 × 4KB ≈ **360GB** + 二级索引 ~90GB | 8 库 × (数据 60GB+索引 15GB)，每库 2TB 云盘足够 |
| 用户域存储 | 8000 万 × 3KB ≈ 240GB（归档前） | 8 库 × 100GB 起步 |
| ES | question_doc 9000 万 × 2KB ≈ 180GB × 1 副本 = **360GB** | 6 数据节点（各 2T NVMe）+ 3 专用 master |
| Redis | 热题 20 万 × 4KB + 会话/篮/计数/布隆(9000 万位≈11MB×N) ≈ **6GB 常驻** | Cluster 3 主 3 从（各 8GB） |
| 读 QPS 画像 | 假设日活 300 万（8000 万注册的 3.75%），人均 20 次读/日 ≈ 70 QPS 均值，**峰值×20 ≈ 1400 QPS**（模考季/开学季） | 缓存命中 95% 后 DB 读 ≈ 70 QPS——**瓶颈在缓存与网关，不在库**；网关横向扩容即可 |
| 写 QPS | 组卷行为/下载记录/任务上报 ≈ 峰值 300 QPS | 批量化后单库轻松承接 |
| 出口带宽 | 题目页静态资源全走 CDN；源站仅 API JSON（P95 8KB） | 源站带宽 1Gbps 起步，图片/SVG/文档 CDN 卸载率 >90% |

### 2.4 中间件规格清单

| 组件 | 生产规格 | 高可用 | 关键参数 |
|---|---|---|---|
| MySQL 8.0 | 8 分片 ×（主 16C64G NVMe 2T + 从同规格） | 一主一从半同步，跨 AZ；gh-ost 变更 | innodb_buffer_pool≈内存 70%；慢查 0.2s |
| ShardingSphere-Proxy | 4C16G ×2（前置 LB） | 无状态双活 | 逻辑槽 64 固定，扩库只改映射 |
| Redis 7 Cluster | 3 主 3 从，各 8GB | cluster 模式跨 AZ | maxmemory-policy noeviction；AOF everysec |
| Elasticsearch 8 | 3 master(4C16G) + 6 data(8C32G, 2T NVMe) | 双索引别名全量重刷 | shard 数=数据节点数；ik 分词 |
| RocketMQ 5 | 2 主 2 从 | 事务/延迟/顺序消息全用上 | binlog topic 分区按 question_id 保序 |
| ClickHouse | 8C32G ×2 | 学情/行为/归档分析 | practice/behavior 明细 90 天分区 |
| 对象存储 | OSS + CDN（或 MinIO 4 节点起步） | immutable 路径 /fig/{yymm}/{sha256} | 生命周期：临时导出文件 7 天过期 |
| Canal/MQ 连接件 | 4C8G ×2 | binlog→Kafka→ES/缓存失效 | es-lag P99 < 10s 告警 |
| browserless 渲染池 | 8C16G ×3 | 导出 PDF 队列驱动 | 并发渲染 2/实例，超时 90s |

### 2.5 成本粗算（云上月度，供预算评审）

| 块 | 构成 | 月成本（¥） |
|---|---|---|
| 数据库 | 8×（主+从 16C64G）+ 交易/配置库 2 套 | ~6.5 万 |
| K8s 计算 | 3 master + 8 worker 16C64G（包年 7 折） | ~3.5 万 |
| ES | 9 节点 | ~2.2 万 |
| Redis/MQ/CH | 中间件全家桶 | ~1.5 万 |
| 带宽+CDN+高防 | 1Gbps + 流量 + WAF | ~2.0 万 |
| 可观测+备份存储 | SaaS 化优先 | ~0.8 万 |
| **合计** | | **~16.5 万/月（staging 另计 ~1/4）** |

> 演进触发器：单表 >800 万行、网关 P99 >300ms 持续 1 周、Redis 内存 >70%、es-lag >60s——任一命中即启动扩容评审（64 逻辑槽内扩库不动路由）。

### 2.6 高可用与容灾

- 同城双 AZ 部署（K8s/中间件跨 AZ），MySQL 主从跨 AZ 半同步；RPO≈0，RTO<10 分钟（从库提升）。
- 异地容灾：xtrabackup 全量 + binlog 实时传异地对象存储；ES 双索引支持重建；核心配置（Nacos 快照）随镜像走。
- 降级预案：ES 挂 → 选题走 DB 分片键点查+章节树浏览（题目详情不受影响）；MQ 挂 → 导出退化为同步小卷；CDN 挂 → 图片走源站限流。
- 全链路压测：staging 用影子表跑 2× 峰值（开学季模型），卡点进 GA 验收（docs/08）。

## 3. GitHub 大用户量项目设计模式借鉴落地表

### 3.1 数据库设计借鉴（分库分表/大表治理）

| 源项目 | 它怎么做 | 落地到我们 |
|---|---|---|
| **12306**（亿级票务） | 订单按 user_id 分片 + **按订单号冗余一份查询表**解决"乘客查别人的单"；余票用计数缓存不实时算 | 题目/试卷分片键唯一化；paper_question 快照冗余（docs/04 已有）就是同思路——**查询维度冗余表，不跨片 JOIN**；download_record 带 paper_hash 做 30 天重复判定同理 |

### 3.2 优惠券/营销设计借鉴（lilishop / newbee-mall / 天机学堂）

| 设计点 | 业界通行做法（lilishop、newbee-mall 秒杀版、天机学堂 promotion） | 我们的实现（docs/14/16 + 本轮代码） |
|---|---|---|
| 券域模型 | 券模板（规则）→ 用户券（实例）→ 核销流水 三层分离 | coupon_template / user_coupon / order.coupon_id 三层已落地；类型 满减/折扣/点数券 |

| 领取限次 | 每人限领 X 张（查历史）+ 活动期每日限领 | perLimit + **dailyPerLimit（天天领券，本轮新增列）**；唯一索引兜底并发 |

| 预算中心（美团模式） | 发券总量受"营销预算"闸门控制，防运营手滑 | P2 演进：coupon_batch 预算表 + 超发熔断告警 |
| CDK 激活码 | 一次一用、防猜、可停批 | **本轮落地**：去歧义字符集（无 0/O/1/I/L）+ 14 位展示格式 + 码占坑条件更新 + 批次停用过期 + 双保险（码状态 & 批次计数都条件更新），事务回滚保证"校验失败不烧码" |
| 任务/积分 | 任务定义表 + 完成记录表（唯一键幂等）+ 发奖流水 | **本轮落地**：task_def/task_record/point_log 三表，period=yyyymmdd 或 LIFETIME，重复上报返回 duplicate 不报错（自动上报友好） |
| 签到 | BitMap 按月存储（hmdp/天机学堂） | 现为 sign_record 行存（可审计）；P2 增加 Redis BitMap 月视图缓存加速"连续天数"展示 |

### 3.3 缓存/稳定性借鉴（hmdp / damai / 12306）

| 模式 | 落地 |
|---|---|
| 缓存三防（穿透/击穿/雪崩） | docs/27 §9.5：空值缓存+布隆过滤器 / Redisson 逻辑锁单飞 / 随机 TTL |
