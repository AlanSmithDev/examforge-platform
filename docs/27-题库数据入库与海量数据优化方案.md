## 2. 入库总体架构（六阶段流水线）

```
┌────────┐  ┌────────┐  ┌──────────┐  ┌────────┐  ┌──────────────┐  ┌───────────────┐
│ E 抽取 │→│ C 清洗 │→│ N 规范化  │→│ D 去重 │→│ Q 质量分级/打标 │→│ L 装载(生产+ES+缓存) │
│Extract │  │Clean   │  │Normalize │  │Dedup   │  │Quality        │  │Load           │
└────────┘  └────────┘  └──────────┘  └────────┘  └──────────────┘  └───────────────┘
 jsonl/csv   BOM/乱码/   枚举对齐/     MD5精确+     规则机审+        staging→生产(幂等)
 sqlite      HTML残留    难度分箱/     simhash      LaTex校验/       binlog→Canal→Kafka
 回放        图片提取    字段映射      合并策略     素养/考点打标     →ES宽表/缓存失效
```

- 运行形态：**批处理为主（每日增量 + 全量重刷能力）+ 预留 Kafka 流式入口**（UGC/AI 产题实时进）。
- 实现载体：Python 3.11（orjson/pandas/reedsolo 不需要）+ MySQL LOAD DATA + 后续 ShardingSphere 旁路写入；代码位置规划 `code/enterprise/examforge-service/ingest-svc`（独立部署，不占在线服务资源）。
- 铁律：**一切写生产都从 staging 出发，禁止爬虫直连生产库**；每批次可回放、可回滚（§5.4）。

### 3.2 学科字典（先建后导）

`subject` 表预置全量字典（学段×学科），与 `题库/_meta/学科目录.json` 的 164 目录做一次性对齐：匹配项发正式 subject_id；新增学科（中职护理、临床医学等）按 docs/11 矩阵插入，`alias` 列存爬虫侧叫法（如"道德与法治"↔"政治"）。

### 3.3 枚举归一

**题型**（question_type 源值 → 枚举）：单选题/单选→1；多选题→2；填空题/概念填空→3；解答题/计算题/证明题/应用题→4；判断题→5；作图/实验探究→6；作文/翻译→7（语言类特殊题型，ext 保留原值）。**细分题型**（如"填空-单空题""多选题-3个答案"）入 `sub_type` 列，运营可配（组卷网同构筛选）。

**难度分箱**（与组卷网"适中(0.69)"展示对齐，难度系数=得分率，越大越易）：

| difficulty_coef 区间 | 档位 | 展示 |
|---|---|---|
| [0.85, 1.00] | 1 | 容易 |
| [0.70, 0.85) | 2 | 较易 |
| [0.50, 0.70) | 3 | 适中 |
| [0.30, 0.50) | 4 | 较难 |
| [0.00, 0.30) | 5 | 难 |

> 注意：源数据"越大越难"与学科网"系数越大越易"相反——清洗阶段做 `coef = 1 - difficulty`（源 difficulty 越大越难时）。**以抽样 20 题人工核对为准后固化规则**，此规则错一半的后果是全站难度倒挂。

## 5. 批量导入实施

### 5.1 装载方式选型

| 方式 | 适用 | 我们的选择 |
|---|---|---|
| `LOAD DATA LOCAL INFILE` | CSV 大文件首装 | ✅ question.csv 331MB 一条命令级（实测口径 ~66 万行/分钟级） |
| 程序分批 INSERT（批 5000，多值 VALUES） | JSONL 增量、需要逐题变换 | ✅ 流水线主路径 |
| `INSERT ... ON DUPLICATE KEY UPDATE` | 幂等重放 | ✅ 以 source_qid 唯一键兜底 |
| mysqldump/走 ShardingSphere 代理 | 生产分片表写入 | ✅ 生产段经代理（分片路由由它接管），staging 段直连 |

### 5.2 清洗规则集（代码级约定）

1. 编码统一 utf-8-sig；去除 U+FEFF/零宽字符；全角空格转半角。
2. HTML 残留剥离（`<sub>/<sup>/<br>` 转语义标记）；Markdown 残留（`**`/`__`）剥离。
3. 换行归一：题干内换行保留（解答题分小问），选项内换行删除。
4. LaTeX 规范化：`\left.` 补全、定界符配对校验（KaTeX renderable lint，失败进 Q 质量工单 `latex_fail`）。
5. 数值/单位规范化留待"内容治理"阶段（不阻塞上架）。

### 5.3 指纹与去重（承接 simhash_dupes.json 已有成果）

- **精确指纹**：`norm_stem_hash = md5(去空白去标点去数字变量的题干)` —— 同卷同题跨批次必杀。
- **近似指纹**：simhash64（汉明距离≤3 视为疑似重），仅做**同科**内比较（跨科比较无意义且省 90% 算力）；分桶：`shard = simhash >> 56` 建索引加速近邻。
- **合并策略**：保留 quality 高者；knowledge 并集；answer 冲突（同题不同答案）→ 双双打 `suspect_answer_conflict` 进工单，**不自动选边**；被并题在 id_map 记 `merged_into`（历史组卷引用不断链）。

### 5.4 批次状态机与可回放

```
LOADED ──► CLEANED ──► NORMALIZED ──► DEDUPED ──► QUALITY ──► MERGED ──► ARCHIVED
   │fail      │fail         │fail          │fail        │fail        │fail
   └──────────┴─────────────┴──────────────┴────────────┴────────────┴──► FAIL(记录 step, 可从该步重放)
```

每步产物写 `ingest_batch.artifact_uri`（中间结果 JSONL 落 MinIO/本地），任何一步失败从该步重放，不整批重来。**MERGED 步是唯一写生产库的步骤**：事务内 staging→生产 upsert + id_map 落账 + 批次计数对账（期望行数 vs 实际行数，差 1 即回滚）。

## 6. 知识点、素养与考点治理

1. **导入暂存知识点**：`knowledge_points[]` 自由文本先建 `knowledge_point(stage=TMP)` 节点（is_temp=1），保证题目可检索上架。
2. **归并**：编辑后台提供"暂存知识点→正式树"拖拽归并工具（批量移动+合并），归并后 question_knowledge 批量改挂；组卷网式考法/素养标签（docs/26 F-XKW-04）由规则+模型补打：素养六维（数学运算/逻辑推理/直观想象/数学建模/数据分析/抽象概括）按知识点映射表初打，模型复核。
3. **目录先行**：77 个空学科目录已有 kid，先灌章节树（教材版本→册→章→节），题目后到。

## 9. 海量数据优化专项（9000 万题 / 8000 万用户，v2 口径）

### 9.1 容量测算（决定架构的数字）

| 项 | 估算 | 依据 |
|---|---|---|
| question 主表行数 | 9000 万 ÷ 64 逻辑槽 = 每表 **~140 万行**（远低于单表 2000 万警戒线） | 分片数是一次性决定、扩容贵的资源，定稿 **8 物理库（学科垂直）起步 + 预留逻辑槽 64**（取模 64，物理库 8 → 每库 8 表，扩库到 16 不改路由）；用户域 8 库 × 32 表 = 256 槽（每表 ~31 万行） |
| question 总存储 | 题干+选项+解析均值 4KB/题 → 内容域 **~360GB**；索引 ~90GB | 全学段均值估计，临床医学类长题干按 2× 冗余设计；8 库 ×（数据 60GB + 索引 15GB） |
| 用户域 | 8000 万 × (user+member+point+practice≈3KB) → ~240GB | practice 90 天归档后常驻 <60GB |
| ES | question_doc 9000 万 × 2KB ≈ 180GB × 1 副本 = **360GB** | 3 专用 master + 6 数据节点（docs/28 §2.4） |
| Redis | 热题 20 万 × 4KB + 会话/篮/计数/布隆 ≈ **6GB 常驻** | Cluster 3 主 3 从（各 8GB） |
| QPS 画像 | 日活 300 万（注册 3.75%），读峰值 ≈1400 QPS（×20 开学季系数）、写峰值 ≈300 QPS | 缓存命中 >95% 后 DB 读 ≈70 QPS——瓶颈在缓存与网关，不在库（docs/28 §2.2） |

### 9.2 分库分表落地参数

```yaml
# ShardingSphere-JDBC 关键配置（question 域示意，用户域同理换键）
rules:
  sharding:
    tables:
      question:
        actual-data-nodes: ds${0..7}.question_${0..7}   # 8 物理库 × 8 表 = 64 逻辑槽
        database-strategy:
          standard: { sharding-column: subject_id, sharding-algorithm-name: q-db }
        table-strategy:
          standard: { sharding-column: id, sharding-algorithm-name: q-tbl }
    sharding-algorithms:
      q-db:  { type: INLINE, props: { algorithm-expression: ds${subject_id % 8} } }   # 按学科垂直分库
      q-tbl: { type: SNOWFLAKE_MOD, props: { sharding-count: 8 } }                     # 按主键水平分表
```

- **学科垂直分库**是题库业务天然切分（跨学科查询不存在——选题永远带学科），比纯 user_id 哈希更贴业务；学科冷热不均（临床医学 48%）用**库内再分表 + 大学科独立库**（subject_id=临床医学 单独 ds）解决。
- 禁令重申：无分片键的 UPDATE/DELETE 禁止上线（SQL 审计卡点）；跨片 JOIN 一律改 ES 宽表。
- 全局唯一 ID：Leaf-snowflake（时间有序利于 InnoDB 页顺序写），worker-id 经 ZooKeeper/DB 号段分配。

### 9.3 索引优化清单（大表索引是预算，不是默认）

| 表 | 必建 | 禁建/慎建 | 理由 |
|---|---|---|---|
| question | PK(id)；`(subject_id,question_type,difficulty)` 组合（选题高频）；`(source_type,year)` | 不建 status 单列索引（区分度低，走组合前缀） | 低区分度索引入 ES，不进 MySQL |
| question_knowledge | `(kp_id,question_id)` | — | 知识点→题目是 ES 职责，此表仅补数用，覆盖索引即可 |
| question_content | PK(question_id) | **不建 latex_text 索引** | like '%x%' 索引无效，文本检索全部走 ES |
| user | PK(id)；`mobile_blind`(盲拍哈希) | 不建 nickname 索引 | 后台找用户走 ES 用户宽表 |
| paper | `(user_id,update_time)` | — | 深分页禁用（§9.7） |

- 单表索引 ≤5 个、索引列总宽 ≤ 行宽 1/3；上线前 EXPLAIN 全量 review（CI 卡点，参考 12306 做法）。

### 9.4 冷热分离与归档

| 数据 | 热 | 冷 | 动作 |
|---|---|---|---|
| practice_record / behavior | 90 天 | ClickHouse | XXL-Job 每日归档，MySQL 保留分区裁剪 |
| question_stats 历史 | 当日计数 Redis | 月表 | 计数回写见 §9.6 |
| 已下架/驳回题 | — | 归档库（同结构 ds_archive） | status 变更即迁，主表只留 id+status 防断链 |
| 试卷快照 paper_question.question_snapshot | 定稿 180 天 | OSS JSON | 大 JSON 出库，行内只留 uri |

### 9.5 缓存体系（读路径 95% 命中目标）

| 层 | 内容 | 策略 |
|---|---|---|
| Caffeine（应用内） | 学科/章节树/知识点树/题型字典 | **永不过期 + MQ 变更广播刷新**（docs/04 §3 既定） |
| Redis | 题目详情聚合 JSON（题+选项+答案解析打包） | TTL 24h + content_version 版本号失效；随机 TTL ±10% 防雪崩 |
| Redis | 试题篮/收藏态/每日配额 | hash 结构，TTL 30d |
| 防穿透 | 空值缓存(60s) + 布隆过滤器(题目ID, 5000万位) | 未上架题 ID 直拒 |
| 防击穿 | 热题重建加 Redisson 逻辑锁 | 单飞回源 |

### 9.6 计数与统计优化

- use_count/favor_count/download_count：**Redis INCR 先行，XXL-Job 每 5 分钟批量回写 question_stats**（回复制 UPDATE ... SET x=x+delta，避免行竞争）；卷引用数在试卷定稿时异步入队。
- 前台展示口径（"378,523 道试题"）：ES count 缓存 5 分钟，不做实时 count(*)。

### 9.7 查询治理

- 深分页一律 cursor（`WHERE id < ?` 游标）或 ES search_after；`LIMIT 100000,20` 进慢 SQL 黑名单。
- 慢查询治理：`long_query_time=0.2s` 接入 SkyWalking + 每周 top10 review；强制走分片键的 SQL 审计在 ShardingSphere `sql-federation` 关闭下自然报错兜底。

### 9.8 运维侧

- DDL 变更：gh-ost（大表禁止原生 ALTER）；窗口避开 9 月模考季（docs/19 既定）。
- 备份：Xtrabackup 每日全量 + binlog 实时 → 异地；ES 双索引别名支持全量重刷。
- 监控指标（Grafana 看板新增）：入库流水线各阶段积压量、es-lag（binlog→ES 延迟秒）、缓存命中率、单表行数水位（>2000 万告警即触发扩容预案：64 逻辑槽扩物理库）。

### 9.9 导入期专项（一次性动作不污染常态）

首装/大批次导入会话临时调参：`SET unique_checks=0; foreign_key_checks=0; innodb_flush_log_at_trx_commit=2;`（**批次结束必须还原为 1/1/1**）；question 表**先导数据后建二级索引**（9000 万级建索引耗时 > 写入本身）；导入窗口业务只读或低峰。

## 10. 导入 Runbook（命令级步骤）

```bash
# 0) 预检：三方口径对账（JSONL 行数 vs SQLite 题数 vs CSV 行数），差异 >0.5% 停下查因
python ingest.py audit --root 题库/ --report out/audit.json

# 1) 建辅助库表
mysql -h ingest-db < sql/27_import_pipeline.sql

# 2) 批次登记 + LOADED：JSONL/CSV 原样入 staging（sha256 登记，断点续传）
python ingest.py load --batch B20260928-01 --src 题库/ --format jsonl --chunk 10000

# 3) CLEANED → NORMALIZED：清洗 + 枚举映射 + 难度分箱（规则版本号入 batch）
python ingest.py clean  --batch B20260928-01
python ingest.py norm   --batch B20260928-01

# 4) DEDUPED：精确指纹 + simhash（复用 _meta/simhash_dupes.json 跳过已剔除 qid）
python ingest.py dedup  --batch B20260928-01 --reuse-simhash 题库/_meta/simhash_dupes.json

# 5) QUALITY：机审规则 + LaTeX lint + 素养/考点打标
python ingest.py quality --batch B20260928-01

# 6) MERGED：staging → 生产（经 ShardingSphere 代理，事务 + 对账 + id_map 落账）
python ingest.py merge  --batch B20260928-01 --dsn "mysql://proxy:3307/examforge"

# 7) 同步 ES 全量重刷（双索引别名切换）+ 抽样验收
python ingest.py es-reindex --alias question
python ingest.py verify --sample 2000 --report out/verify_B20260928-01.html
```

## 11. 验收标准

1. **对账零差**：批次期望行数 = staging 行数 = 生产 question 新增行数 + id_map.merged 行数。
2. **抽样正确率 ≥99%**：2000 题人工复核（字段映射/难度档/答案解析完整性）。
3. **枚举覆盖 100%**：无未归一题型/学段残留（SQL group by 检查）。
4. **去重有效**：同指纹题目数为 1；simhash 疑似重复清单只减不增。
5. **ES 一致性**：生产与 ES 计数差 <0.01%，es-lag P99 < 10s。
6. **性能基线**：60 万题/小时装载速率（单机流水线即可达成）；生产点查 P99 < 20ms（缓存命中路径）。
7. **可回放**：任一历史批次从 FAIL 步重放成功，生产行数不变（幂等证明）。
