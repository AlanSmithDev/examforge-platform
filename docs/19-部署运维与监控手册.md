## 2. MVP 单机部署 Runbook（code/app）

### 2.1 环境变量清单

| 变量 | 必填 | 说明 |
|---|---|---|
| `PORT` | 否 | 监听端口，默认 3000（`server.js:75` 实际读取） |
| `JWT_SECRET` | **必改** | 生产必须显式设置强随机串；代码存在开发兜底值 `'examforge-dev-secret-change-in-prod'`（`server/auth.js:5`），**严禁生产沿用**。生成：`openssl rand -hex 32`（Git Bash 与 Linux 通用） |
| `NODE_ENV` | 建议 | `production` 时 `/payments/mock-notify` 硬禁用（403）——沙箱回调生产防护已实装 |
| `AI_PROVIDER` | 否 | `MOCK`（默认，离线确定性输出）/ `OPENAI_COMPAT` |
| `AI_BASE` | AI 实连必填 | OPENAI 兼容端点（如 `https://api.deepseek.com/v1`）；**SSRF 白名单**：仅 http/https、禁环回/内网/本地域名，内网自建 vLLM 需 `AI_ALLOW_PRIVATE=1`，校验失败自动降级 MOCK |
| `AI_KEY` / `AI_MODEL` | AI 实连必填 | Bearer 密钥与模型名；15s 超时失败降级 MOCK（degraded=1） |

数据目录：`server/data/`（`examforge.db` + `-wal` + `-shm`），容器化时必须挂卷持久化该目录。
**上线标准改造实况（2026-09-28）**：SQLite 连接调优（`busy_timeout=5000/synchronous=NORMAL/foreign_keys=ON`）；schema_migrations 序号化迁移（health 返回 schemaVersion 供运维核对）；登录限流（同 IP 5 次/分内存版，生产换 Redis）；traceId 贯穿（响应头 X-Trace-Id + 错误日志）；**优雅停机已实现**（SIGTERM/SIGINT → server.close → db.close，10s 超时强退，systemd `KillSignal=SIGTERM` 即触发）。

### 2.2 进程守护（三选一）

**方式 A：systemd（Linux 生产推荐）** `/etc/systemd/system/examforge.service`：

```ini
[Unit]
Description=examforge-app MVP
After=network.target
[Service]
WorkingDirectory=/opt/examforge/app
Environment=PORT=3000 NODE_ENV=production
EnvironmentFile=/opt/examforge/app/.env        # JWT_SECRET 放这里，权限 600
ExecStart=/usr/bin/node server/server.js
Restart=always
RestartSec=3
User=examforge
[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now examforge   # Linux
```

**方式 B：pm2（Windows/Linux 通用；与现有部署指南一致）**：

```bash
cd /e/code/business/zujuan-platform/code/app   # Git Bash；Linux 为 /opt/examforge/app
npm i -g pm2
pm2 start server/server.js --name examforge --time --max-memory-restart 512M
pm2 save && pm2 startup     # 开机自启（Windows 下用 pm2-installer 或改用方式 C/计划任务）
```

**方式 C：Docker（镜像构建见 `code/app/Dockerfile`，node:18-alpine）**：

```bash
docker build -t examforge:1.0.0 .
docker run -d --name examforge --restart unless-stopped -p 80:3000 \
  -e PORT=3000 -e NODE_ENV=production \
  -e JWT_SECRET=$(openssl rand -hex 32) \
  -v /data/examforge:/app/server/data \
  examforge:1.0.0        # 挂卷持久化 SQLite；Git Bash 下 $() 同样可用
```

### 2.3 升级步骤（停机窗口 < 1 分钟）



## 3. 企业版部署（code/enterprise，docker-compose）

### 3.1 拓扑图（文字版，对应 `enterprise/docker/docker-compose.yml`）

```
客户端(Vue3 教师端 :5173 / 超管端 :5174)
   │ HTTP
   ▼
gateway :8080 ── JWT 全局校验/路由聚合/限流（JWT_SECRET 环境变量注入）
   │ 直连服务地址（QUESTION_URL/RENDER_URL 等；注册中心 Nacos 为 03 文档规划项，compose 现状为直连）
   ├─ user :8101 ──────┐
   ├─ question :8102 ──┤            ┌─ mysql :3306（8.0，挂载 ../sql 自动初始化，healthcheck=mysqladmin ping）
   ├─ paper :8103 ─────┼── 共用 ────┼─ redis :6379（7-alpine，缓存/会话）
   ├─ admin :8104 ─────┤  dbenv     └─ elasticsearch :9200（8.13.4，题目搜索，可降级 DB LIKE）
   ├─ trade :8105 ─────┤
   ├─ practice ────────┤── question(:8102)
   ├─ ai（AI_PROVIDER 默认 MOCK）──┐
   └─ render（browserless/chromium :3100→3000，HTML→PDF）
数据卷：mysql-data / redis-data / es-data（升级前必须快照，见 §6）
```

### 3.2 服务启动顺序

1. **数据层**：`mysql`（等 `service_healthy`，compose 已用 healthcheck 约束）→ `redis` → `elasticsearch`（首次启动建索引 `sql/es-question-mapping.json`）。
2. **基础服务**：`user` → `question`（其余服务依赖其接口）→ `trade`/`admin`/`practice`/`ai` 可并行（均依赖 mysql 健康）。
3. **边缘**：`render`（渲染 worker）与基础服务无启动依赖，可提前并行拉起；`gateway` 最后启动（depends_on 全部业务服务）。
4. 规划项：接入 Nacos 后，启动顺序变为 **nacos → mysql/redis/es → 基础服务（注册+拉配置）→ gateway**；XXL-Job 调度中心随数据层启动（§4 定时任务迁移到 XXL-Job 执行器）。

```bash
cd /e/code/business/zujuan-platform/code/enterprise/docker   # Linux: /opt/examforge/enterprise/docker
JWT_SECRET=$(openssl rand -hex 32) docker compose up -d      # 首次自动执行 sql/ 初始化
docker compose ps                                            # 全部 healthy/running 后验收
curl -fsS http://localhost:8080/api/v1/health                # 网关聚合健康检查
```

### 3.3 健康检查端点约定（全服务统一）

| 语义 | 判定 | 运维动作 |
|---|---|---|
| `/api/v1/health` 返回 `{"code":0,...,"db":true}` | **存活+就绪**（MVP 现实现：`db=true` 表示可查到用户记录，即 DB 连通） | K8s readiness/liveness、SLB 后端健康检查、compose healthcheck 均以此为准；`db:false` → 触发 §7 数据库预案 |
| 下游依赖降级 | ES 不可用时 question 服务应**降级返回 DB LIKE 结果**而非 5xx（README-ENTERPRISE 既有设计），health 仍为 true | 告警由指标层触发（§5），不摘流量 |
| 启动期 | 服务启动 30s 内 health 不通 → compose `restart: on-failure` 自动重拉；连续 5 次失败 → 人工介入看服务日志 | 禁止无 healthcheck 就挂 SLB |

### 3.4 优雅停机

```bash
docker compose stop gateway trade      # 先停流量入口与交易写服务，让在途请求/事务结束（默认 10s，超时 SIGKILL）
docker compose stop -t 30 question paper   # 渲染/组卷长任务给足 30s 落盘（导出任务断点由 MQ/任务表恢复）
```

- 原则：**先摘流量（网关/SLB 摘后端）→ 停交易服务 → 停只读服务 → 最后停数据层**；MySQL/Redis/ES 属数据层，严禁随业务发布重启。
- 应用侧约定：监听 SIGTERM 后停止接新请求、在途请求最长 25s 内完成、Spring `server.shutdown=graceful`；MVP Node 无长任务，直接 `stop` 即可。

## 4. 定时任务运维表（商业化关键任务）

> MVP 阶段以 node-cron/@schedule 进程内实现（单写节点天然不并发）；企业版统一迁 XXL-Job（03 文档 job-scheduler）。执行机时间必须 NTP 对时（每日任务集中在 0 点段）。

| 任务 | 频率 | 逻辑（对应表/状态机，见 `enterprise/sql/05_trade.sql`） | 幂等性 | 失败重试与告警 |
|---|---|---|---|---|
| 超时关单 | **每分钟** | `UPDATE trade_order SET status='CLOSED' WHERE status='CREATED' AND expire_at < NOW()`（30 分钟未付，docs/14 O-3）。现表无 `expire_at` 列，等价条件 `created_at < NOW() - INTERVAL 30 MINUTE`，建议加冗余列+索引便于扫描 | 天然幂等：CAS 式条件更新，仅 `CREATED→CLOSED`，重复执行 0 行受影响 | 单次失败重试 3 次（间隔 1min）；连续 3 轮失败 P2 告警（订单积压监控兜底：CREATED 超 40min 存量>100 单即告警）。迟到的支付回调遇 CLOSED 单：不履约，走原路退款并 P1 告警人工跟进 |
| 券过期 | **每日 00:10 定时 + 惰性双保险** | 定时：`UPDATE user_coupon SET status=2 WHERE status=0 AND expire_time<NOW()`（0未用→2过期）；惰性：查询/核销时校验 `expire_time`，过期即置 2（下单核销主路径兜底） | 条件更新幂等；以 `status=0 AND expire_time<NOW()` 为界，重跑无副作用 | 定时失败重试 3 次、P2 告警；即使定时任务整体失联，核销/展示侧惰性校验保证过期券不可用，**不产生资损** |
| 会员到期扫描 | **每日 00:30** | 扫 `member.expire_time < NOW()`：会员权益失效（entitlement 判定失效+缓存失效），**点数余额保留**（docs/14 M-4）；批量置权益快照并发通知 | 按 `expire_time` 判定，天然幂等；扫描窗口取“自上次成功扫描以来”避免漏扫 | 重试 3 次后 P2 告警；任务失败不影响权益正确性（entitlement 按 expire_time 实时判定），仅影响通知触达 |
| 签到重置 | **每日 00:00** | 清连续签到标记：对昨日无签到记录的用户连续计数清零（签到日历表按 `user_id+day` 唯一索引防刷，docs/14 P-5/K-3）；当日首次签到 +1 点入 `point_log(reason=REWARD)` | 以日期为幂等键：同一 day 的重置/入账按唯一索引去重，重跑不重复加分 | 重试 3 次、P2 告警；影响仅积分体验，不影响资金 |
| 支付对账 | **每日 01:00 对 T-1** | 拉渠道账单 vs `payment_callback`（回调流水）vs `trade_order`（订单状态）：三方核对笔数与金额；差异落对账差异表（差异单冻结人工处理） | 以“账单日期”为幂等键，重跑覆盖当日差异结果 | 拉单失败重试 3 次退避（5/15/30min）后 P1 告警；**差异笔数 >0 即 P1 告警**，24h 未闭环升级 P0；对账是回调丢失（§8.1）的主发现手段 |

通用要求：所有任务执行写运行日志（开始/结束/影响行数/耗时）；任务自身有 `last_success_at` 心跳，**心跳超 3 周期未更新即告警**（防任务静默死亡）。

## 5. 监控指标体系

| 分类 | 指标 | 采集方式 | 告警阈值 | 级别 | 处置动作 |
|---|---|---|---|---|---|
| 业务 | 下单量（`trade_order` 新增/min） | 订单表分钟计数 | 环比昨日同时段骤降 >50% | P1 | 排查下单链路/渠道入口，联动前端埋点 |
| 业务 | **支付成功率**（PAID/(PAID+CLOSED+失败回调)） | 回调+订单状态统计 | **<99.9% 即 P0**（P0 电话告警，5min 未恢复拉起应急） | P0 | 验签失败？渠道故障？白名单误拦？→ §8.1/§9 回调白名单排查；必要时切 MOCK 供应商止血并公告 |
| 业务 | 券核销率（USED/发放） | `user_coupon` 状态统计 | 偏离运营基线 ±30% 或 granted>total | P2 | 立即核对模板库存；`granted>total` = 超发，直接进 §8.2 预案 |
| 业务 | 点数消耗速率与 42900 触发率 | `/trade/consume` 响应码统计 | 42900（余额不足）触发率 >5% | P2 | 区分正常余额耗尽 vs 计费异常/刷接口；`point_account.balance<0` 任意一笔即 P1 → §8.3 |
| 业务 | 对账差异数 | 对账任务产出 | >0 笔 | P1 | 差异单冻结、人工核对渠道账单（§4） |
| 技术 | P99 延迟（网关/核心接口） | Nginx/网关访问日志或 APM | >1s 持续 5min | P2 | 看慢 SQL/连接池/渲染 worker 排队；>3s 持续 5min 升 P1 并限流非核心接口（03 §4.3 降级矩阵） |
| 技术 | HTTP 5xx 错误率 | 访问日志按 code 统计 | >0.5%（5min） / >2%（1min） | P1 / P0 | 摘除故障节点；看错误日志 traceId 定位（§6） |
| 技术 | MySQL 连接池使用率 | 连接池指标/`SHOW PROCESSLIST` | >80% 持续 10min | P2 | 排查慢查询/泄漏；超 95% 升 P1，临时扩 maxPool |
| 技术 | SQLite WAL checkpoint 滞后 | `-wal` 文件大小 + checkpoint 耗时（MVP） | WAL >64MB 或 checkpoint >5s | P1 | 手动 `PRAGMA wal_checkpoint(TRUNCATE)`；持续增长 → 排查长事务/读连接阻塞，必要时低峰重启 |
| 技术 | Redis 内存/命中率、磁盘使用率 | redis_info / node_exporter | 内存 >80%、磁盘 >80%（>90% 升 P1） | P2 | 扩容/清理过期键；磁盘满会直接打挂 SQLite/MySQL 写入，优先处理 |
| 技术 | 证书与心跳 | blackbox 探测 `/api/v1/health` | TLS 剩余 <30 天；health 连续 3 次探测失败 | P2 / P0 | 见 §7 安全基线 / 摘节点重启 |

## 6. 日志规范

**结构化字段约定**（单行 JSON，MVP 输出至 stdout/stderr 由守护进程收集，企业版进 ELK/SkyWalking 关联 traceId）：

| 字段 | 说明 |
|---|---|
| `ts`/`level`/`svc` | ISO8601 时间、ERROR/WARN/INFO、服务名（MVP 固定 `examforge-app`） |
| `traceId` | 网关生成（MVP 为请求中间件生成的短随机串），全链路透传，日志/告警以此串联 |
| `orderNo`/`uid` | 交易日志必带订单号与用户 ID（脱敏：手机号仅留前 3 后 4） |
| `route`/`code`/`costMs` | 接口路径、业务 code（如 42900）、耗时毫秒——costMs 是 P99 指标数据源 |

**保留策略**（等保三级 + 财务要求，冷数据归档对象存储）：

| 日志类型 | 热存 | 归档保留 |
|---|---|---|
| 应用日志（INFO/ERROR） | 30 天（ES/本地文件） | 1 年 |
| 网关访问日志 | 30 天 | 180 天（《网络安全法》≥6 个月） |
| **操作审计日志**（后台/admin/点数人工调整 `/trade/points/adjust`） | 90 天 | **3 年**（等保要求，防篡改：归档桶开启 WORM/合规保留） |
| **支付流水**（`payment_callback`/对账差异/退款记录） | 1 年在线 | **10 年**（财务凭证要求，年度归档校验可读性） |

**日志轮转**：Linux 用 logrotate（`/var/log/examforge/*.log` daily rotate 30 compress）；Windows/pm2 用 `pm2 install pm2-logrotate`（10MB 分片、保留 30 个）；Docker 用 `--log-opt max-size=10m --log-opt max-file=30`。轮转后的归档文件按上表定期搬运对象存储。

## 7. 安全基线运维

1. **JWT_SECRET 轮换（每 90 天）**：新值 `openssl rand -hex 32`（Git Bash/Linux 通用）。MVP 为单密钥，轮换即全量 token 失效——安排低峰（工作日上午）+ 提前公告，用户重新登录；企业版网关规划 kid 双密钥滚动验证（新旧并行 24h）。轮换后监控登录接口成功率 30min。
2. **支付密钥/证书轮换（每年或渠道要求）**：微信/支付宝商户 API 密钥与平台证书按渠道指引轮换，**新旧密钥并行验签窗口 ≥24h**；轮换当晚对账任务（§4）人工盯防，差异即回滚。
3. **内网回调白名单**：支付回调仅接受 POST 且来源 IP 必须命中白名单（docs/14 O-6）。白名单配置在环境变量/配置中心，**变更走工单+双人复核**，季度审计一次（比对渠道官方最新回调 IP 段）；误拦会直接表现为支付成功率下跌（§5 P0）。
4. **证书到期监控**：所有 HTTPS 域名纳入 blackbox 探测（证书剩余天数指标，<30 天 P2、<7 天 P1）；Let's Encrypt 域名用 acme.sh/certbot 自动续期 + 续期后 reload Nginx/网关。
5. 生产账号基线：种子超管 `13000000000/Admin@123456` 首次部署后立即改密；`.env`/compose 中任何密钥禁止提交仓库（现有 compose 的 dev 默认 JWT_SECRET 仅限本地）。

## 8. 事故预案

每条均按 **发现 → 止血 → 根因 → 复盘** 四步执行；P0/P1 事故复盘 48h 内出报告，改进项进迭代。

### 8.1 支付回调丢失（用户已扣款、订单未变 PAID）
- **发现**：对账任务差异单（§4 主手段）；或用户客诉/工单。
- **止血**：以 `order_no` 调渠道查单接口主动反查——已支付则**以幂等方式补履约**（同一事务：PAID→券核销→开会员/加点数→流水，docs/14 O-5），补单打 `来源=补偿` 标记入审计；未支付则告知用户原路退回。
- **根因**：回调网络丢包 / 验签失败 / 白名单误拦 / 服务端 5xx 且渠道重试已耗尽。
- **复盘**：把查单补偿从“人工/对账触发”固化为**每 5 分钟主动查询 CREATED 超过 5min 的订单**的兜底任务；回归白名单与验签变更流程。

### 8.2 券超发（`granted > total` 或同一券被重复核销）
- **发现**：券核销率/库存监控（§5）或对账；用户侧“领到不可用券”投诉。
- **止血**：后台将 `coupon_template.status` 置下线——**冻结模板**，阻断继续领取与发放；已发放券保留（不可追溯作废已用券），未用超发部分按用户名单批量置过期。
- **根因**：领取扣减未走乐观锁/唯一索引，并发穿透 `total` 上限（docs/14 C-3）。
- **复盘**：审计日志回溯发放流水定位突破点；修复后必须补“并发领券/并发核销”压测用例（验收标准见 14 §9），模板创建默认开乐观锁字段检查。

### 8.3 点数负余额（理论上不可能：P-1 明确余额不可透支，出现即并发缺陷）
- **发现**：巡检 `SELECT user_id FROM point_account WHERE balance<0` 告警（纳入 §5 业务指标分钟巡检）。
- **止血**：**冻结账户**（标记禁止消费与提现，保留全部流水），核对 `point_log` 成对性；小额负差额由平台侧 `point_log(reason=ADMIN)` 入审计修正，超出阈值按资损流程上报。
- **根因**：扣减与余额校验非原子/乐观锁 version 未生效，两笔并发扣减同时通过校验。
- **复盘**：用并发回归用例复现；修复强调“校验+扣减同一事务/同一行锁”，`/trade/consume` 加幂等键防重扣。

### 8.4 数据库损坏（SQLite `database disk image is malformed` / MySQL 库表损坏）
- **发现**：`/api/v1/health` 返回 `db:false`、接口 500 激增、备份任务报错。
- **止血（SQLite）**：立即停写（`sudo systemctl stop examforge` 或 `pm2 stop examforge`）；**保全现场**（拷走 `examforge.db/-wal/-shm` 三件，勿删 WAL）；用最近备份恢复——
  ```bash
  litestream restore -o /data/examforge.db s3://examforge-backup/db/examforge.db   # 或直接取每日冷备
  rm -f /data/examforge.db-wal /data/examforge.db-shm && sudo systemctl start examforge
  curl -fsS http://localhost:3000/api/v1/health      # 验证 db:true 后切流
  ```
  MySQL 走“最近 xtrabackup 全量 + 增量 + binlog 重放至故障点”（见 §9）。
- **根因**：磁盘坏块/进程崩溃时 WAL 写入不完整/文件系统故障；用日志与 `dmesg`、磁盘 SMART 定位。
- **复盘**：校验 litestream 实际 RPO 是否达标 5min；巡检常态化——每日冷备前执行 `PRAGMA integrity_check`（MVP）/`CHECK TABLE`（MySQL），失败即 P1。

## 9. 备份与容灾

| 对象 | 方案 | RPO | RTO | 保留 |
|---|---|---|---|---|
| SQLite（MVP） | ① litestream 常驻实时复制 WAL 到对象存储（秒级追踪，承诺 RPO=5min）；② 每日 02:00 冷备：停写窗口 `sqlite3 examforge.db ".backup ..."`（或 `VACUUM INTO`）后上传 OSS，冷备前 `PRAGMA integrity_check` | 5min | 30min（新机装 Node+代码 → `litestream restore` → 起服务 → DNS/SLB 切换 → smoke） | 日备 30 天、月备 12 个月 |
| MySQL（企业版） | XtraBackup 每周日全量 + 每日增量 + binlog 实时归档到对象存储；关键 DDL 前手动手备份 | <1min（binlog） | 2h（恢复+验证） | 全量 30 天、binlog 14 天、月备 12 个月 |
| 配置/密钥 | compose/.env、Nacos 配置导出、白名单清单纳入版本化备份（密钥存 KMS/密码库，不入 git） | 随变更 | — | 永久 |

**恢复演练（季度强制）**：每季度在隔离环境执行一次真实恢复并记录耗时——
1. 取最近一次全量（SQLite 冷备或 xtrabackup）恢复到隔离机；2. 起服务跑 `npm run smoke`（MVP）/ 服务单测+health（企业版）；3. 抽查 5 条交易订单/点数流水与线上比对；4. 记录实际 RTO，超标的瓶颈（下载带宽、恢复脚本）列入改进项；5. 演练报告归档（等保三级测评材料）。
